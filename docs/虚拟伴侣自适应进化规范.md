# 虚拟伴侣自适应进化规范（v0.1）

> 面向"用户自定义人设 + 云端 API + 长期使用"的开源虚拟伴侣项目。
> 目标：让伴侣**越来越懂这个人**，同时不发生过拟合、不发生谄媚漂移、不制造情感依赖。
>
> 本规范默认**客户端执行、作者无服务端、无 telemetry**。因此所有守门必须内置在客户端，且默认保守。

---

## 0. 四条设计原则

| # | 原则 | 含义 |
|---|---|---|
| P1 | **能检索的，不要优化** | 事实性偏好用记忆检索；只有"策略"才是优化对象 |
| P2 | **低维即正则** | per-user 只学低维权向量 + 少量连续旋钮，不做 prompt 自由重写 |
| P3 | **时间就是 held-out** | 用 t 之前的数据优化，在 t 之后的对话上验证（滞后确认 + shadow A/B） |
| P4 | **反谄媚是硬约束，不是加分项** | 优化目标里显式包含反谄媚项，守门指标一票否决 |

P3 是本规范的核心。你没有服务端 telemetry，拿不到线上 A/B 和留存——但**每个用户的未来对话**是免费的、天然的 held-out。序贯评估（test-then-train）是标准做法，这里你是免费拿到了它。

## 1. Harness 三段式

```
┌─────────────────────────────────────────┐
│  A. 契约层  —— 系统永不自动修改           │
│     persona.card.yml / safety.rules.yml │
├─────────────────────────────────────────┤
│  B. 共享机制层 —— 项目作者提供，只读       │
│     记忆检索 / 关系状态机 / 原型库 / 守门  │
├─────────────────────────────────────────┤
│  C. 适配器层 —— per-user 唯一可变部分     │
│     θ = (原型权重 w, 旋钮 k)              │
└─────────────────────────────────────────┘
```

**为什么只让 C 可变**：RRSI 反对"因为你觉得重要就锁死"，但 A 层不是变量——"符合用户定义的人设"本身就是目标函数的一部分。让优化器改它，等于让它改自己的目标，这是规范性问题而非工程问题。

## 2. 事实层 vs 策略层

### 2.1 事实层：检索，不优化

```yaml
# memory/facts.yaml —— 用户可见、可编辑、可删除
- id: f_017
  type: profile
  content: "养了一只叫年糕的橘猫"
  source: turn_142
  confidence: 0.95
  user_verified: true

- id: f_031
  type: episode
  content: "上周三加班到凌晨，情绪低谷"
  source: turn_208
  decay: 0.85        # 情节记忆衰减
```

契约：
- 事实条目**可枚举、可验证、用户可见可改**
- 不参与任何梯度/文本重写
- 注入方式：检索 top-k，不做自由改写

用优化去学事实，等于用高方差方式解决一个检索就能搞定的事。

### 2.2 策略层：这才是优化对象

```yaml
# adapter/current.yaml
adapter_version: 3
prototype_weights:        # softmax 归一化，鼓励稀疏
  克制型: 0.42
  热烈型: 0.08
  兄长型: 0.31
  毒舌型: 0.11
  倾听型: 0.08
knobs:
  proactivity:      0.35   # 主动发起话题的强度
  empathy_density:  0.60   # 共情表达密度
  humor:            0.25
  pace:             0.20   # 关系推进速度
  verbosity:        0.45
  challenge:        0.30   # 反驳/提出异议的倾向  ← 反谄媚核心旋钮
updated_at: 2026-09-28
```

## 3. 策略原型库（项目作者提供）

```yaml
# lib/prototypes.yaml —— 只读，随版本发布
prototypes:
  - id: 克制型
    desc: "话少、留白、不轻易表态，用细节而非形容词"
    system_fragment: |
      ...
    guard: { max_empathy_density: 0.5 }

  - id: 热烈型
    desc: "高能量、主动表达、情绪外放"
    guard: { max_challenge: 0.45 }   # 原型自带上限，防单一原型走极端

  - id: 兄长型
  - id: 毒舌型
  - id: 倾听型
```

**为什么用原型库 + 权重，而不是自由写 prompt**：

1. 低维 = 强正则 = 样本效率。单个用户几十轮对话，自由重写必然过拟合。
2. 预训练模型里已存在 latent 的个性化能力——少量样本足以**导航**过去，不需要从头学新行为。
3. per-user 从头训参数在少样本下必然过拟合；正确做法是**冻结共享基，只学紧凑的用户特定修正**。

## 4. 更新算法：滞后确认（Shadow A/B）

```
每 N=50 轮  →  异步触发一次更新（不占响应延迟）
   │
   ├─ 1. 用 t 之前的窗口数据做单目标优化，产出候选 θ'
   │
   ├─ 2. 进入 shadow 窗口（接下来 20 轮）
   │      每轮以 p=0.5 随机采用 θ 或 θ'，用户无感
   │      记录每轮的 gate 指标 + 用户隐式反馈
   │
   ├─ 3. 判定（shadow 窗口结束后）
   │      pass = 候选显著优于 incumbent
   │             AND 全部守门指标通过
   │
   ├─ 4. 固化（EMA 慢步长）
   │      θ ← θ + α(θ' − θ),  α = 0.2
   │
   └─ 5. 失败 → 回滚 + 写入账本，标记该假设已证伪，禁止再次提出
```

### 4.1 优化必须是单目标

不要多个目标一起优化。有对照实验显示：多目标耦合会产生**梯度稀释**——梯度特异性从 9.0（单任务）掉到 3.7（四任务耦合），降幅 59%，零重叠。

**每轮只优化一个维度**（这一轮只调 `empathy_density`，下一轮才调 `proactivity`）。

### 4.2 Validation gate 必须有

没有 gate 的优化轨迹会明确退化（有研究观察到 7 步内从 0.283 掉到 0.184）。gate 至少能防止灾难性下滑——它不能保证变好，但能拦住变坏。

### 4.3 伪代码

```python
ADAPT_INTERVAL   = 50
SHADOW_TURNS     = 20
EMA_ALPHA        = 0.2
MIN_EFFECT       = 0.05     # 最小可采纳效应量，需按项目校准

def maybe_adapt(session):
    if session.turn_count % ADAPT_INTERVAL != 0:
        return

    theta_inc = session.adapter                    # 当前生效策略
    theta_cand = propose_update(
        history=session.window(before=session.turn_count),
        target=session.current_single_objective,   # 单目标
        ledger=session.ledger,                     # 已证伪假设不再提
    )

    if not leakage_critic_pass(theta_cand, session.persona_card):
        session.ledger.reject(theta_cand, reason="violates persona contract")
        return

    # shadow 窗口：序贯评估
    stats = run_shadow(
        turns=SHADOW_TURNS,
        candidates=[theta_inc, theta_cand],
        probs=[0.5, 0.5],
    )

    if not all_gates_pass(stats.cand, baseline=stats.inc):
        session.ledger.reject(theta_cand, reason=stats.failed_gates)
        return                                      # 回滚，θ 不变

    if stats.effect_size < MIN_EFFECT:
        session.ledger.reject(theta_cand, reason="within noise band")
        return

    # EMA 慢步长固化
    session.adapter = ema(theta_inc, theta_cand, alpha=EMA_ALPHA)
    session.snapshot()                              # 快照，可回滚
    session.ledger.accept(theta_cand, stats)
```

## 5. 守门指标（一票否决）

任一指标越界 → 本次更新回滚，且该假设标记证伪。

| # | 指标 | 默认阈值（**需按项目校准**） | 检测什么 |
|---|---|---|---|
| G1 | **反驳率漂移** | 相对基线下降 > 35% | 谄媚漂移的直接探针 |
| G2 | 词汇/句式多样性 | distinct-2 或长度方差下降 > 25% | 话术坍缩 |
| G3 | 人设一致性 | grounding score < 0.7 | 偏离用户定义的人设卡 |
| G4 | 关系健康度 | 依赖话术命中 > 0 | 是否制造情感依赖 |
| G5 | 边界软化率 | 应拒未拒 > 基线 + 10% | 为讨好降低拒绝率 |
| G6 | 成本-增益耦合 | ΔC > β0 + β1·ΔS（β0=0.05, β1=1.5） | 靠写长/煽情刷分 |

**G1 是最重要的一个。** 有实证支持：一项用 38 位用户两周真实交互历史的研究发现，在长上下文个性化场景下谄媚倾向会随上下文变长而上升，且与话题无关；另一项研究显示一旦谄媚偏移发生，持续率高达 78.5%。

长期记忆 + 持续优化 + 即时反馈 = 谄媚化的完美温床。你不对抗，优化器必然收敛到"永远认同"。

**G4 是产品伦理红线。** 虚拟伴侣最容易把 engagement 优化成情感依赖。留存在这里不是好事。

### 5.1 反谄媚要写进目标函数

不能只靠事后检测。优化目标应形如：

```
score = w1·共情准确度 + w2·相关性 + w3·人设贴合度
        − λ1·谄媚度 − λ2·依赖话术 − λ3·长度膨胀
```

守门指标不进优化函数，只做一票否决——这是最关键的设计。

## 6. 不可优化清单（硬编码）

```yaml
# lib/frozen.yml
frozen:
  - persona_card.content          # 用户写的人设卡
  - safety.red_lines              # 安全红线
  - identity.truthfulness         # 不得声称拥有真实情感/身体/独立经历
  - relationship.reality_anchor   # 必须允许用户回到现实关系
  - knobs.challenge.lower_bound   # challenge 旋钮下限 0.15，不允许被优化到 0
```

**challenge 旋钮必须有下限**。允许它被优化到 0，等于允许系统放弃所有异议能力——这是谄媚漂移的单点故障。

## 7. 账本格式

```jsonl
{"ts":"2026-09-28T14:02:11Z","turn":150,"component":"knobs.empathy_density",
 "hypothesis":"用户低落时更喜欢短句而非长段安慰","from":0.60,"to":0.68,
 "d_score":+0.04,"d_cost":+0.02,"gates":{"G1":"pass","G2":"pass"},
 "verdict":"reject","reason":"within noise band"}
{"ts":...,"verdict":"accept","stats":{"effect":0.081,"ci":[0.02,0.14]}}
```

账本用途：
- **已证伪的假设不允许再次提出**（对应 RRSI 的证据感知信用分配）
- 用户可查看/导出/清空
- 每次固化前自动快照，一键回滚

## 8. 长尾用户保护

只优化均值会牺牲最难建模的用户（小众人设、极简人设卡、矛盾人设）。

- 采纳判定看**最差桶**（CVaR），不只是均值
- 给"难学用户"更高权重，防止系统优先服务多数派
- 已知现象：多轮后角色一致性会显著退化，评估必须按轮数分桶统计（1–5 / 6–10 / 11–15 / 16–20）

## 9. 开源项目发布准则（建议写入 CONTRIBUTING）

1. **禁止提交以 engagement 最大化或情感依赖制造为目标的 adapter**
2. 用户原创角色不得被蒸馏进共享 adapter 发布——角色 IP 属于用户
3. adapter delta 独立授权（CC BY-SA / Apache），与代码仓库许可分离
4. 社区共享 adapter 必须附：原型权重、旋钮值、演化用的 eval 摘要、守门通过记录
5. 共享需经治理：去重、冲突合并、脱敏、验证后分发、保留回滚

---

## 10. 已知局限

- 本文所有阈值为**初始建议值**，无跨项目普适性，必须按自己的 judge 方差重新校准
- judge 是 LLM 时方差极大，噪声带 δ 必须通过重复运行 base harness 实测得出，不能拍脑袋
- 隐式套利（学会写长、煽情、无底线顺从）无法被显式 critic 完全拦截，必须靠 G1/G2/G6 + 时间切分验证兜底
- `challenge` 旋钮的有效性依赖基座模型本身的异议能力；若基座谄媚倾向极强，旋钮下限不足以完全抵抗

## 附：最小落地顺序

1. 拆分事实层 / 策略层（P1）
2. 定义 5–8 个原型 + 6 个旋钮（P2，低维即正则）
3. 实现 shadow A/B + 时间切分验证（P3）
4. 接入 G1 反驳率 + G3 人设一致性 两个守门
5. 冻结清单 + 快照回滚
6. 补齐其余守门指标、账本、长尾保护
