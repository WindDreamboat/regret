# 虚拟伴侣应用 — 需求简报与开发里程碑

## 一、产品定义

一款移动端虚拟伴侣应用，核心体验是**有记忆、有性格的日常聊天陪伴**。用户可以自由定制伴侣的性格、背景故事，伴侣通过本地维护的**记忆系统与状态模型**维持持续的人格状态和关系记忆，并在对话中体现情感变化。

---

## 二、已确认决策汇总

| 决策项 | 选择 |
|--------|------|
| 产品定位 | 有记忆、有性格的日常聊天伴侣 |
| 大模型 | 国内模型（DeepSeek 云端 API） |
| 平台方案 | Web 端包装成 App（Capacitor） |
| 认知逻辑位置 | **前端单端（TypeScript），不做端侧 Rust 移植** |
| 语言方案 | **TypeScript**（V1 单端） |
| 记忆存储 | **IndexedDB**（V1）；**不做向量检索** |
| 情绪表达 | **模型输出结构化状态 + 自然语言表达**（非 PAD 映射表） |
| 用户账号 | 不需要登录（数据存本地） |
| 对话体验 | 文字 + 表情/emoji |
| 伴侣性格定制 | 自由定制（用户自定义性格、背景故事） |
| 技术背景 | 4 年开发经验，主流语言基本都行 |

> 决策变更说明：原方案为"用 Rust 重写 LAAP 认知核心并移植到端侧"。经评估，其收益与成本严重倒挂，已改为前端 TypeScript 编排层方案。详见第四节。

## 四、架构决策：为什么不移植 LAAP

原方案计划用 Rust 重写 PSI 循环、情绪引擎、记忆索引、注意力，再通过 JNI / C FFI / WASM 桥接三端。放弃的三条理由：

1. **收益不确定**。产品差异化来自"记忆准"和"人设稳"，这 80% 取决于记忆检索质量与 prompt 编排质量。PSI 的需求驱动与目标选择是为自主智能体设计的，对陪聊场景的边际收益从未被验证。
2. **成本确定且高昂**。Rust 重写 + 三端绑定 + 情绪参数调优，是排期里最大的一块。
3. **端侧的两个理由都撑不住**。端侧运行只为省成本与保隐私；但认知引擎不跑推理，省不下服务器钱；而 LLM 调用本身走云端，隐私优势只有一半。

**结论**：把认知工程降级为 prompt 编排层，用最快路径验证产品，留存成立后再决定是否下沉为独立内核。

对照原方案的裁剪：

| 原方案 | 现方案 |
|--------|--------|
| Rust 重写 PSI 认知循环 | 取消 |
| Rust → JNI / C FFI / WASM 三端绑定 | 取消 |
| 五层记忆（含程序记忆） | 缩减为三类（对话流 / 事实 / 关系状态） |
| 向量记忆（usearch） | 取消，改为结构化 KV 全量注入 |
| PAD 三维 + emoji 映射表 | 改为模型输出结构化情绪状态 |
| 端侧 SQLite | IndexedDB |
| 迭代 1-2 纯 Rust、不接 UI | 迭代 1 即产出可试用产品 |

保留的部分：自我模型（改为关系状态）、注意力（改为记忆选择性注入）、LLM 适配层（改为 PromptComposer）。

## 五、记忆系统设计

### 5.1 存储选型

**IndexedDB（通过 Dexie）**，表结构按关系型设计以便未来上云。

不使用 sql.js / wa-sqlite：wasm 包 1MB+，与"Android 安装包 < 30MB"的目标冲突。

### 5.2 表结构

```
messages    : id, sessionId, role, content, ts
facts       : key(PK), value, category, confidence, validUntil?,
              sourceMsgIds[], firstSeenAt, updatedAt
relations   : id(=1), stage, intimacy, addressForm,
              sharedExperiences[], boundaries[], updatedAt
summaries   : id, level, coversFromId, coversToId, content, ts
moodLog     : id, ts, mood, energy, affectionDelta, triggerMsgId
```

`facts` 以 `key` 为主键，采用**覆盖式更新**，不做追加。

### 5.3 写入路径

抽取拆成两条路径，**主链路永远只有一次 LLM 调用**：

| 路径 | 内容 | 时机 | 额外成本 |
|------|------|------|----------|
| 同步轻量 | 情绪、关系状态的小步变化 | 合并进主回复调用，模型在回复末尾附加状态块 | 无 |
| 异步批量 | 事实抽取、摘要 | 距上次抽取 ≥ 6 轮，或页面静默 60s | 离开关键路径 |

状态块格式（前端渲染前剥离）：

```
<state>{"mood":"被逗笑","energy":0.7,"affection_delta":1}</state>
```

### 5.4 事实抽取协议

输入为未抽取的原文 + **当前事实的 key 列表**（用于避免模型自造重复 key）。

```json
{
  "ops": [
    {"op":"upsert","key":"user.drink","value":"美式","category":"preference","confidence":0.9},
    {"op":"delete","key":"user.city"}
  ]
}
```

三个必须处理的边界：

- **改口**：`upsert` 覆盖，不残留冲突事实。
- **时效**：事件类必须带 `validUntil`（如"下周面试"），过期自动归档，不进 prompt。
- **误抽**：`confidence < 0.6` 先存 `pending`，同一事实第二次出现才升为 confirmed。

### 5.5 读取路径（prompt 组装）

```
[固定]   人设卡（性格 / 背景 / 说话风格）      ← 用户改人设才变
[固定]   输出协议 + 状态块格式说明
[半固定] 关系状态（自然语言渲染）              ← 每轮小变
[半固定] 事实记忆（按 key 字典序）             ← 缓慢变
[滚动]   最新 1-2 条摘要
[滚动]   最近 N 轮原文
```

三条硬性规则：

1. **事实渲染为自然语言**，不用 JSON 字面量（更省 token、模型理解更好）。
2. **事实排序必须按 key 字典序**，不能按更新时间——否则每次顺序抖动，上下文缓存前缀全部失效。
3. **事实软上限 300 条**，超出按 `category 权重 × confidence × 引用次数` 淘汰进归档区（保留在库中，不进 prompt）。

system prompt 中必须约束模型**不得点破记忆机制**（禁止"根据我的记忆……"这类出戏表达）。

### 5.6 摘要

未摘要消息超过 40 轮，将最老的 20 轮压为一条 level-1 摘要；level-1 累积到 10 条合并为 level-2。prompt 中只注入最新 1-2 条 level-1 与 1 条 level-2。

摘要 prompt 要求：保留具体事实与情感事件，丢弃寒暄；摘要中抽出的新事实同样需走一遍 ops。

### 5.7 明确不做

- **不做向量检索**：陪伴类对话的记忆规模小（一年几百条事实），全量注入比向量检索更准——向量检索会漏召回，而漏召回在陪伴场景中表现为"你忘了我说的"，直接损害核心体验。待事实超过 1000 条再评估。
- **不做记忆可视化管理界面**：用户不会去编辑记忆。

### 5.8 记忆验收标准

| 场景 | 期望 |
|------|------|
| 覆盖 | 第 15 轮询问"我喜欢喝什么"，能答对 |
| 改口 | 先说喜欢猫、后说怕猫，之后不再说喜欢猫 |
| 时效 | 说"下周面试"，两周后不再主动提及 |
| 出戏 | 注入 200 条事实，回复不出现"根据我的记忆"类表达 |
| 延迟 | 引入记忆后，主链路延迟无变化（抽取全异步） |

## 六、LLM 与成本

### 6.1 模型选型

| 模型 | 上下文 | 缓存命中输入 | 缓存未命中输入 | 输出 |
|------|--------|-------------|---------------|------|
| deepseek-flash | 1M（待核实） | 0.05 元/M | 1.5 元/M | 4.5 元/M |
| deepseek-v4-pro | 1M（待核实） | 0.15 元/M | 4.5 元/M | 13.5 元/M |

（空闲时段价格）

V1 使用 **deepseek-flash**：成本可控，支持长上下文与 Tool Calls。

> **待核实**：表中上下文长度与价格需在开发前对照官方文档确认。上下文长度不影响"不做向量检索"的结论，只影响摘要触发的频率。

### 6.2 缓存策略

上下文缓存依赖 prompt 前缀稳定，与 5.5 节的排序规则直接相关。事实区块的字典序输出是缓存命中的前提。

### 6.3 API Key 保护

纯前端直连 DeepSeek 会使 API Key 打包进 App，抓包即可获取。V1 仍需要一个**极轻的转发代理**（一个 serverless function 即可）。

> **决策变更（迭代 4 期间）**：原定「Key 只放代理、绝不进前端」已放宽为**页面可配**——App 的「设置 → 连接」页可填 API Key，明文存于设备 localStorage，随请求头透传给自建代理；客户端留空时代理回退到自身 `.env`，两种用法并存。
> 取舍：换取「打包后不必为换 Key / 换模型 / 换代理地址而重新构建」的可用性；代价是 Key 落在设备上，且会出现在代理访问日志里（需脱敏）。仅适用于个人自用设备，代理仍必须做来源白名单与限流。

> **决策变更（迭代 4 收尾）**：代理**不再是技术必需**，降为可选。原先「必须有代理」的硬理由只有跨源：打包版 WebView 来源是 `https://localhost`，厂商接口不回 CORS 头时浏览器 fetch 直接被拦（实测主流网关 `gateway.example.com` 的预检返回 `405`）。现已由 App 侧的原生回退解决——浏览器 fetch 失败时改由系统网络栈发请求，原生请求没有同源策略（见 `src/adapters/llm/nativeFetch.ts`，真机已验证）。**取舍**：回退路径是整包返回、没有逐字流（厂商本身一次性返回时无差别）；代理保留的价值只剩「Key 不落设备」与「服务端限流」，个人自用设备可直接用直连模式省掉部署。

## 七、产品与留存

### 7.1 竞品现状

该赛道已相当拥挤：星野 / 猫箱（国内）、Character.AI、Talkie、Replika。

- "自由定制性格"**不构成差异化**——所有竞品都支持。
- "隐私优先"是好故事，但难以成为付费理由。
- 真正仍存空白的是：**记忆的深度与准确**（竞品普遍记不住）与**主动说话的时机感**（竞品普遍是定时打扰）。

对应到工程投入：原本准备投在 PSI 认知循环上的精力，应改为投在"记住什么"与"何时主动开口"上。

### 7.2 留存钩子

V1 最值得押注的是**后续追问**——"昨天那个面试怎么样了"。它仅依赖记忆系统即可实现，且正命中竞品弱项。

主动推送（陪伴类产品的核心留存手段）受限于 Capacitor 的后台唤起能力，V1 不实现，改为**用户打开 App 时的补偿性问候**。

### 7.3 冷启动体验

首次进入时用户面对空白界面，需在 3 分钟内让其产生"这就是我要的"的感受。这是留存的第一道关口，需在迭代 3 专项打磨。

### 7.4 评测集（必需）

建立手工评测集：20-30 个多轮对话脚本，每轮检查"是否记得此前内容"与"是否符合人设"，人工打分。修改 prompt 后重跑。

没有评测集，prompt 调优将完全依赖手感，无法收敛。

## 九、开发里程碑

### 迭代 1：对话闭环

**目标**：产出可部署、可给真实用户试用的最小产品。

**交付物**：
- React 对话界面 + 人设配置页
- `core`：`ChatProvider` 接口、`PromptComposer`、消息类型
- `adapters`：`DeepSeekAdapter`、转发代理
- 对话持久化到 IndexedDB

**验收标准**：
- 可连续对话，刷新页面不丢失
- 部署到公网，**给 5 个真实用户试用**

### 迭代 2：记忆系统

**目标**：让伴侣真正"记住"。

**交付物**：
- `MemoryStore` 接口 + `IdbMemoryStore` + `InMemoryStore`（测试替身）
- 事实抽取（异步批量）+ ops 应用 + 守卫校验
- 关系状态与状态块（合并进主调用）
- 分层摘要

**验收标准**：
- 通过 5.8 节全部五条记忆验收标准

### 迭代 3：情感与留存

**目标**：形成留存钩子并建立可度量的调优闭环。

**交付物**：
- 情绪 / 关系状态的前端展示
- 后续追问机制
- 手工评测集 + 跑分脚本
- 冷启动体验打磨

**验收标准**：
- 评测集通过率达标
- 后续追问能准确引用历史事件

### 迭代 4：打包与优化

**目标**：可安装的移动端产物。

**交付物**：
- Capacitor Android 打包配置
- 记忆导出 / 清除（设置页）
- 性能与体积优化

**验收标准**：
- Android 安装包可安装运行，体积 < 30MB
- 长对话响应延迟 < 2s（含 API 调用）
- 无明显崩溃或内存泄漏

> V1 不做 iOS 绑定。
